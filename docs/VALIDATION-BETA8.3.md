# 3.0-beta8.3 验证记录

日期：2026-11-21。基于 R7 的修复分支；版本号 13 / 3.0-beta8.3，沿用原签名。

## 原来的重连故障

小米 10S / Android 11 / MIUI 12.5.8，从手机连接 Win11。首次配对可以播放，关闭手机蓝牙再开启后，手机提示连接后立即断开，Windows 没有可用声音输出。

R8.2 中的队列保护已消除连接失败后每约 60–100ms 自行重试的循环，但没有解决实际连接失败：原生回调报告 `SDP record not found`，随后发送失败事件，A2DP 状态回到 0。重新配对只是恢复当次播放；用户再次关开蓝牙后仍复现。因此，重新配对不是最终修复。

## 本轮修复

接收模式下，Win11 的服务发现结果没有 AudioSource 记录，但它实际可以建立音频发送传输。精确分析设备原库的 `bta_av_a2dp_sdp_cback`：已有 `skip_sdp` 路径在缺失记录时使用保守的 AVDTP 1.2 版本，继续后续传输发现、配置和连接。R8.3 仅在本地服务 UUID 为 AudioSink（0x110b）时，允许走同一条现有路径。

这一步只继续实际协商，未修改“已连接”事件、流端点能力、配对或系统权限检查。发送模式、已有成功的 SDP 结果及原 `skip_sdp` 路径保持原行为。若对方无法提供传输或正确流端点，仍由原有状态机报错/超时。

原库 SHA-256：

`169d1823c3a0d6d07fd87da84632317fbc793f82e1dd956e573a057a5e652adb`

同时包含 AVRCP 空列表保护、重复入队保护及本轮 SDP 兼容路径，结果 SHA-256：

`e45acdc768aff7f1ab1b70f723e8d46038aaf6ec8da31f765abfbf5b74ad17b9`

新增指令区域为 0x1139f0 的 68 字节；只作用于上述完整哈希匹配的库。在本机生成副本并临时挂载；不分发厂商库，不写系统分区，发送模式卸载。可从 R8/R8.2 的已知旧补丁迁移。

接收服务接口获取仍使用 R8.2 的短时前台辅助服务；它 8 秒后结束，不循环重启蓝牙。没有把临时设备类型试验纳入代码：重新配对后 Windows 仍返回手机类型，证据不足以将故障归因于类型缓存。

## 已验证

- R8.3 安装并加载后，13:45:19 仍收到 SDP 缺失结果，13:45:20 随后建立 AVDTP，A2DP 状态由 1 变为 2，RootCommand 返回实际连接成功，Windows 声音端点恢复为 OK。
- 保留配对，连续两轮用手机系统蓝牙服务关闭/开启。13:46:28、13:46:42 均先收到 SDP 缺失结果，再成功建立 AVDTP 和 A2DP。两轮 `profileReady:true`、已连接 TO_MID，配对保留。测试时自动重连已先于 App 连接命令完成，因此不把两轮描述成“App 显式连接调用成功”。
- 用户随后按要求通过手机设置关开蓝牙、从手机连接 Win11，并验证播放、暂停后继续，回复“正常了”。最终状态查询：A2DP 已连接 TO_MID，`sessionActive:true`、`profileReady:true`，加载 `miui-a2dp-reconnect`。
- 原生实际 ARM64 指令仿真共 21 项：前 12 项覆盖 AVRCP 和队列；新增 9 项运行整个 SDP 回调，对照原始实现，覆盖本地收/发/未知角色、原跳过标记、成功/失败响应、空记录和无效控制块，校验事件、版本、调用保存寄存器和栈。
- ABI、适配候选、连接状态机及开机脚本 5 项测试通过。编译、签名验证和 diff 检查通过。

## 验证边界

已完成本机手动关开蓝牙、主动连接及播放回归。尚未验证手机重启后的恢复、其他电脑及长期稳定性。

当前活动模式为接收，保存的开机默认是发送，开机恢复及 root 钩子已启用；没有擅自改为开机默认接收。
