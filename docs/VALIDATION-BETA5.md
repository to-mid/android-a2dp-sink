# 3.0-beta5 验证记录

日期：2026-11-01。编译入口：本地 SSH `127.0.0.1:7778`，沿用既有签名。

## 本轮变化

- AOSP 角色属性配置与服务获取、方法调用分别检测，不再要求蓝牙 APK 位于 `/apex`。
- 方法匹配同时检查参数类型，支持旧接口、AttributionSource、SynchronousResultReceiver，以及 Android 13 发送端的 `WithAttribution` 方法名。
- 没有 Adapter Binder 接口时，检查系统框架 ProfileConnector；旧系统继续采用应用绑定后 root peekService。
- 诊断 schema 2 分别报告配置、资源覆盖、服务获取、方法调用及是否需要资源辅助 APK。静态检查通过仍不代表播放验证通过。
- 修复部分 Android 版本 `cmd overlay help` 输出有效帮助却返回非零时的误判。
- 10S 的高通私有配置仍限定在已验证的 thyme / API 30；没有把厂商属性直接套用于其他手机。

## 测试

`tests/test-bluetooth-abi.sh` 在 JDK 17 上通过，覆盖直接调用、归属信息、回传对象、发送端方法名别名、无归属信息的回传、同参数数量的不同重载、系统返回 false、空列表、超时、无返回结果及未知参数形式。超时与缺失结果不会被当作操作成功。

| 设备 | 实机接口 | 本轮回归结果 |
| --- | --- | --- |
| 10S / MIUI Android 11 / Magisk | service-peek / direct | 完整角色切换与恢复测试通过 |
| MIX2 / Android 15 / KernelSU | adapter-binder / attribution | 完整角色切换与恢复测试通过 |
| K20 Pro / Android 13 / Magisk | 待重新运行探针 | ADB 未授权，尚未验证 |

两台已连接设备的完整检测前后快照一致：角色属性、资源覆盖、蓝牙开关与调试设置未被诊断修改。集成测试检查了双向角色切换、对应服务与 UUID、关闭蓝牙时切换仍保持关闭、重复开启和重复恢复不增加开关记录、启动恢复函数的重复调用保护及原始属性恢复。

测试结束后，10S 恢复接收模式、蓝牙开启、开机默认发送；MIX2 恢复发送模式、蓝牙开启、开机默认发送。两者均恢复测试前的自动恢复设置。

完整回归在 beta5 的直接调用与归属信息调用实现上完成；随后增加 Android 13 发送端别名与无归属信息回传的匹配，并重新编译、签名检查和运行全部接口测试。未对这个新增路径做 Android 13 实机验证。该路径使用系统框架建立连接，不能用模拟调用测试代替实际连接验证。

最终交付包已覆盖安装到两台设备，二者均通过只读诊断与状态复核，诊断前后快照一致。10S 仍是接收模式，MIX2 仍是发送模式。10S 独立 CLI 的 `profileReady=false` 表示当时没有应用绑定可供 peek 的控制 Binder；目标服务与接收 UUID 已在完整集成测试中确认。这次复核没有连接音频源或活动蓝牙音轨。

本轮没有新增真实音频播放、整机重启、延迟或长时间稳定性测试。10S 上一次活动音轨记录属于 beta4，见 [VALIDATION.md](VALIDATION.md)。
