# 3.0-beta6 验证记录

日期：2026-11-01。版本：`8 / 3.0-beta6`。

## 改动与边界

能力选择不再使用 `Build.DEVICE`、机型、厂商名称或 root 管理器名称。型号仅作为诊断信息显示。旧模块目录名称用于识别已安装的历史配置，不作为机型判断。

角色配置目前识别两类协议：AOSP 的 A2DP / AVRCP 属性，以及蓝牙原生库实际包含对应属性引用且拥有完整角色资源的厂商属性。资源路径独立选择动态覆盖、资源 APK / idmap2 或系统已有焦点资源。内置资源 APK 当前针对 `com.android.bluetooth`；不能把此包强行用于其他目标。

新增 schema 3 诊断，区分静态能力 `capabilityPass`、实际控制调用 `runtimeControllerReady` 和当前音频服务查询 `profileProbe`。实际调用异常时关闭控制入口并显示错误。蓝牙关闭时不为检测开启；旧式服务需要界面绑定时标记 `binding-required`，而不是把它描述成已取得 Binder。

修改配置时保存方案缓存，使用固件指纹、蓝牙 APK 路径及文件状态检查有效性。只读检测不写缓存，修改系统配置前始终重新检测。

这版取消了机型白名单，但没有实现未知厂商协议，也不能补回被固件删除的接收实现。检测通过不代表实际播放通过。

## K20 Pro 故障定位

在已安装的 beta5 上复现：检测显示可控制，但 `status` 返回 `NullPointerException`。探针确认适配器能够创建，异常发生在读取名称触发的 AppOps 栈采样回调中。

在同一个独立 root 进程内，将可选采样配置设为不采样后，名称、地址、扫描模式、配对列表、Android 13 的发送端 ProfileConnector 与回传式设备列表调用均成功。此处理只改变辅助进程的静态字段，不修改系统权限设置，不依赖机型或 SDK 版本分支。beta6 将该处理放入辅助进程初始化。

首次 beta6 实测发现配置类名限定漏掉了系统内部类，导致兼容处理未生效；新诊断正确返回 `controller_error`。最终实现按实际构造器和采样字段访问方法判断，不再限定该配置类的全名。修正后，实际 APK 返回 `runtimeControllerReady=true`、`profileProbe=call-succeeded`。

授权恢复后，K20 Pro 已在最终 APK 上通过完整控制回归：状态查询、双向模式切换、对应服务与本机 UUID、关闭蓝牙时切换仍保持关闭、重复开启与恢复不增加开关记录、启动恢复函数重复调用及原始属性恢复。最终恢复测试前的发送模式、蓝牙开启、默认发送及关闭的自动恢复标志。原始与修复后观察摘要见 [k20pro-control-probe.json](evidence/k20pro-control-probe.json)。

随后 ADB 再次失去授权，额外的界面及实际音频播放验证未完成。本次已通过的是控制回归，不把它记作已通过声音播放。

## 自动测试

接口与能力选择测试均通过：

- 直接接口、归属信息接口、回传对象、发送端方法名别名和无归属信息的回传。
- 参数类型匹配、返回 false、空列表、超时、缺少结果及未知签名。
- AOSP / 厂商配置选择、动态 / 资源 APK / 已有焦点资源选择。
- 缺少属性工具、资源条件不完整、缺少厂商属性引用时拒绝相应方案。

10S 已在 beta6 上通过完整角色切换、关闭状态保持、重复开启与恢复、启动恢复函数重复调用及原始属性恢复测试。检测前后系统快照一致。选择依据为原生库的属性引用、五项资源、idmap2 和实际接口调用；没有机型判断。测试结束恢复开始时的发送模式、蓝牙开启与开机默认发送，自动恢复标志保持开启。

MIX2 也通过完整角色切换、关闭状态保持、重复开启与恢复、启动恢复函数重复调用及原始属性恢复测试，检测前后快照一致。选择依据为 AOSP 属性、动态覆盖及实际归属信息接口调用。最终恢复测试开始时的发送模式、蓝牙开启、开机默认发送及开启的自动恢复标志。

10S 和 MIX2 完整回归之后补充了“服务已运行却不能取得 Binder”的诊断失败判定、错误原因显示和采样配置的结构识别；角色切换实现没有再改动。最终包已覆盖安装到这两台设备，均再次通过只读诊断、实际控制调用与状态复核，检测前后快照一致。K20 Pro 完整控制回归使用最终包。上述控制回归不包含新增的实际音频播放、整机重启或长期稳定性验证。
